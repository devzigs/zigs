# Transaction and approval presentation polish

Baseline: `d1af04c`; authoritative main: `3a6c08e58fcf4a5f84016a4f68c088aea1a8195b`.
Reviewed the supplied `Zigs_App_Wide_Premium_UI_PRD_v3.md` transaction, receive, privacy-operation,
approval, detail and overlay requirements, plus the [original reference mapping](art-direction.md).
Applied financial hierarchy, aligned facts, restrained materials and consistent component geometry.
No new reference artwork or capability is imported; earlier reference-access limitations remain.

## Five improvements

| Weakness | Fix |
| --- | --- |
| Send was too narrow and its amount field floated beside recipient helper text. | Wider transaction dialogs, top-aligned fields and a predictable amount column. Mobile still stacks. |
| Amounts, costs and recipient details lacked clear spatial hierarchy. | Opaque neutral amount wells, readable address/unit roles and consistent cost-row spacing. Exact values, estimates and warnings remain intact. |
| Approval participants looked like loose metadata. | Compact wrapping participant chips with distinct approved boundaries, retaining the actual text/check marks and existing state mapping. |
| Lifecycle and operation forms used inconsistent grouping. | Related lifecycle wells, readable step labels, aligned operation actions and the existing shared SOL field component. Deposit, private send and public withdrawal retain separate disclosures. |
| Overlay/context finishing competed with critical content. | A quieter surrounding veil, solid financial surfaces, consistent instructional wells and compact wallet/network headers. No glass behind amounts, addresses, warnings or QR codes. |

One refinement followed the first comparison: compact wallet/network headers and make long
participant names wrap. Lifecycle typography is scoped to payments. Existing short hover and
state-observer motion are retained; no animation, completion event or state transition is added.

## Checks and isolation

See [validation results](payment-polish-validation.json). Checks cover actual dialogs and scrolled
details, 320/390/768/1024/1440px layouts, light/dark, enlarged text, forced colors, 48px targets and
existing disclosure/dismissal behavior. Both palette contrast checks, lint, 41 executed fast
regression suites and the additional Solana application suite pass. The QR regression suite is
skipped because `qrencode` is unavailable; the QR renderer/payload code is unchanged.

The exact JavaScript delta is three wrapper-property substitutions from inline grid styling to
`sol-send-fields`. All other JavaScript bytes, event handlers, transaction construction, signing,
fees, addresses, network behavior and approval logic are unchanged. No new dependency, native
change, merge or deployment. Existing critical copy and data formatting are unchanged.

Screenshots were reviewed in Chrome desktop and phone-browser emulation. Physical phones,
Safari, screen readers, live funded transactions, successful decoded confirmation and every
legacy/error/finality variant are not newly verified. Inert component screenshots establish
presentation only. No new animation/performance benchmark or QR decoding claim is made.
